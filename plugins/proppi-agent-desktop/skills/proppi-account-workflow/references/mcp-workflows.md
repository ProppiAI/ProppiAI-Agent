Select the returned property UUID. An empty result with `filtered: true` means only that the filters matched nothing: list again without them before telling the member they have no properties. ## Generate and review work

For a brief based on account documents, first resolve the property and inspect the relevant sources. Then call `proppi_start_chat_brief` with `request`, `title`, and the resolved `property_id` when applicable. The request describes the question and evidence scope. **This tool currently has no `document_id` or `document_ids` parameter.** Do not promise that only an exact selected subset will be used: if that restriction is essential, prepare the brief from the retrieved sources in chat or use a supported Member selection flow. Set `allow_thin_context` only when the member explicitly chooses to proceed despite limited evidence.

Retain returned `taskId` and `deliverableId`. Use `proppi_get_task({task_id})` for progress and `proppi_get_deliverable({deliverable_id})` for actual content, source references and state. Present the ready result for review. A request to preview without saving permits a chat draft; starting server work persists a task/draft, so explain that distinction when the request forbids any storage.

After the user approves the exact ready brief, call `proppi_accept_deliverable` with `deliverable_id` and `expected_review_token` copied from that reviewed deliverable's `reviewToken`. Ready Healthy Homes, Inbox-to-Done and rental renewal notice deliverables carry a `reviewToken` too and are accepted the same way, so a draft regenerated after the user's review is refused rather than accepted unseen. On a stale/conflict response, re-read the result; never remove the token to bypass review. `proppi_request_deliverable_changes({deliverable_id,feedback})`, `proppi_retry_chat_brief({deliverable_id})` and `proppi_dismiss_deliverable({deliverable_id})` serve different user intentions; follow their actual returned state. What a change request starts depends on the deliverable: a chat brief's first change request and an Inbox-to-Done revision (up to its revision limit) regenerate the draft and queue its preparation, so track the returned deliverable rather than starting another; a tax summary is re-read from the property's ledger at once and stays ready for review with the updated figures (`finalStatus` `ready_for_review`), so read it again with `proppi_get_deliverable`; for other deliverables it records feedback only, and Healthy Homes and rental renewal revisions start through their preparation tools (below). Listing content and property prefill reject change requests: submit a corrected listing draft, or review the prefill in Member. `proppi_retry_chat_brief` restarts only a failed chat brief.

For general work tracking, use `proppi_list_tasks` (optional `status`, `kind`, `property_id`, `limit`; at most `limit` tasks come back, 50 when it is omitted and 100 at most), `proppi_get_task`, and `proppi_create_task({title,request,property_id?,missing_inputs?})`; `missing_inputs` lists, at most 20, facts the member still has to supply. The task list returns `total` and `hasMore`; when `hasMore` is true it is partial, so ask again with a higher `limit` or, at 100, narrower filters (there is no cursor) before saying no other work matches. A list narrowed by `status`, `kind` or `property_id` holds only the matches and its `message` says so; an empty one means only that the filters matched nothing, so list again without them before saying the member has no work. Task creation records work without starting a generic execution engine. `proppi_answer_task_clarification({task_id,clarification,remaining_missing_inputs?})` supplies missing information. `proppi_approve_task` applies only to a suggested Healthy Homes compliance follow-up, rental renewal review or failed document-stage retry; a document retry can call external processing providers, and source-correction suggestions are review-only. Read the task with `proppi_get_task` first and show the user the work it describes: a suggested task it can approve carries a `reviewToken`, and `proppi_approve_task({task_id,expected_review_token,note?})` needs that token. A suggestion can be rewritten in place by a newer source, so an approval with a token from an earlier read is refused as `stale` with nothing approved; read and review the task again rather than retrying with the old token. `proppi_get_task` reads only the member's own tasks, so a suggestion owned by another member is approved in the Proppi app, not here. It does not accept a deliverable or authorise external delivery. `proppi_cancel_task({task_id})` saves a cancellation proposal; complete the specific approval flow below before reporting cancellation. A `completed` task records that the step was done, not that the member accepted its result: only an `accept_outcome` event in its history records that acceptance, so never report completed work as accepted without one. No tool here records it; the member accepts in the Proppi app.

`proppi_list_deliverables` supports `status`, `job_type`, `limit`, `cursor`; do not invent a `property_id` filter. It lists one status per call, and with no `status` only deliverables ready for review (`listedStatus` says which), so an empty default list does not mean there is no preparing, failed or other work; pass `status` for those. A page holds 25 by default and at most 100; when `hasMore` is true, pass `nextCursor` as `cursor` with the same `status` and `job_type` to read the rest before calling the list complete (with other filters the cursor skips deliverables). These list tools refuse a `status`, `type`, `job_type` or `action_type` value outside their schema with nothing listed; correct the value rather than reading the refusal as an empty list. Check returned property/source association. For attention and calendar work, use `proppi_list_attention_items` (optional `limit`, 20 by default and at most 50, and `days_ahead`; when `hasMore` is true, more may need attention than it listed; it never includes a document whose expiry date has passed, so an empty queue does not mean nothing has lapsed), `proppi_get_attention_history`, `proppi_update_attention_item({item_id,action,snoozed_until?})` with `action` one of `acknowledge`, `dismiss`, `snooze`, `assign`, `unassign`, `resolve` or `reopen` (a decision shared with the Member app and kept in history), `proppi_list_upcoming_events` (optional `limit`, 10 by default and at most 50, earliest first by date and then local time, all-day entries first on a date; a timed event carries `time` and `timezone`, so give the time with its zone rather than only the date; when `hasMore` is true, more events are tracked than it listed; it never lists an event dated before today, so an empty list does not mean no deadline has passed), `proppi_create_event` and `proppi_create_reminder` as requested. Both save a dated calendar entry only: `proppi_create_reminder` sets no reminder notification, so never tell the user it set a reminder (a member entry with the same title and date is updated and keeps any reminders already on it; a property entry with the same title and date is refused; a document entry with the same title is moved to the new date). Record exact dates/timezones and distinguish a saved calendar entry from a delivered message.

## Create a sourced property

1. Read `proppi_get_property_creation_guide({})` and check `proppi_list_properties` for an existing property.
2. Gather the required country/jurisdiction, property sector/type and address. The caller AI performs any requested public research using available browsing; Proppi does not fetch research URLs on its behalf.
3. Build `fields` and `sources` using the guide's current schema. Attach actual user/web provenance to supplied nonempty values. `occupancyType` and `yearBought` must come from the user; public sale history is not proof of the member's purchase year. Keep uncertain/missing facts explicit.
4. Call `proppi_prepare_property_creation({fields,sources})`. Read and show the saved proposal. To replace a proposal, use its saved action ID as `replacesActionId` and review the replacement.
5. With explicit consent to that proposal, call `proppi_approve_property_creation({action_id})`. Report creation only from an executed result containing persisted `propertyReceipt.propertyId`/`propertyUrl`.

For an existing property's `property_prefill` deliverable, direct field-selection acceptance to Member. The MCP accept tool does not apply that deliverable type; do not substitute whole-record acceptance.

## Prepare and publish a listing

The publication workflow currently targets **New Zealand sale listings on Trade Me**. New Zealand residential rentals can be prepared as drafts. Rental approval and publication are blocked. Australian channels and rent, bond and availability details depend on the capabilities returned by the service.

1. Reuse existing work: `proppi_list_campaigns({property_id})`, `proppi_list_platform_listings({campaign_id})`, then `proppi_get_listing_workspace({listing_id})`. When requested and absent, `proppi_create_platform_listing({property_id,purpose,platform:"trade_me"})`, with `purpose` `sale` or `rent`, creates/reuses an empty workspace and campaign. Its ID is a Proppi UUID, not a numeric Trade Me ID, property ID, campaign ID or URL.
2. Read the workspace's revision, readiness and `workflow` suggestions. `proppi_prepare_listing_publication({listing_id,expected_revision})` binds existing eligible connection/preparation work; it does not publish. Ask the owner to confirm that the connected, registered Trade Me Property account has Residential for Sale access before publishing a sale listing. Trade Me checks publishing access separately from connection. Residential for Rent is a separate category permission.
3. Obtain provider choices with `proppi_list_trade_me_listing_choices({listing_id,...})`. Use returned opaque choice IDs and typed attribute metadata. Save requested edits through `proppi_update_listing_workspace({listing_id,expected_revision,...changedFields})`; preserve unmodified fields. Refresh the returned revision after every edit.
4. For AI-authored copy, `proppi_submit_listing_content` saves a reviewable deliverable with `property_id`, `title`, `body`, `draft_kind`, `grounded_on` source document UUIDs, and `listing_id` for `platform_listing`. After review, accepting listing content needs `expected_listing_revision`; the `expected_review_token` requirement does not apply to listing content. Acceptance applies copy and clears old approval, without publication.
5. Upload a supplied photo with `proppi_upload_listing_photo({listing_id,expected_revision,file:...})` or its complete base64 alternative. It appends by default; `isPrimary: true` makes the photo first. Never use `proppi_store` for listing photos. Set ordered existing photos with `proppi_set_listing_photos({listing_id,expected_revision,document_ids})`; first is primary. Use actual user-selected assets.
6. Validate the current draft with `proppi_validate_listing_draft({listing_id,expected_revision,expected_environment?})`; pass `expected_environment: "sandbox"` only for sandbox verification, because a mismatched environment fails before Trade Me is contacted. Validation checks listing fields only, never uploads photos, and grants no approval. Report `sale_restricted` as a confirmed Residential for Sale membership restriction for the checked account. Inspect `proppi_get_listing_publication_preview({listing_id})`. Show content, destination, account/environment, photos and any returned fees or limitations. Do not infer an absent fee as free.
7. Use `proppi_submit_listing_for_review({listing_id,expected_revision})`, then `proppi_approve_listing({listing_id,expected_revision})` only with the member's approval of that exact revision. A request merely to see a draft stops before approval.
8. For an explicitly requested publication, create a saved proposal with `proppi_request_listing_publication_approval({platform_listing_id,idempotency_key})`. Retain the key for that attempt. Show/read the saved action and obtain consent to its actual destination and revision. Approve via `proppi_approve_listing_publication({action_id,confirmation:"publish"})`.
9. Retain returned `publication.operationContextId`. If it was lost (for example after a panel click), recover it from `proppi_get_pending_action` or the workspace's latest attempt; never approve again to obtain it. Call `proppi_get_listing_publication_outcome({operation_context_id})` until the returned state supports the reported outcome. A queued job or an older live URL is not proof the new revision is live. Do not use `job_id` with this tool.

For a membership-type rejection, show the account correction from the publication outcome. Direct the owner to Trade Me connection settings to connect an account with access to the listing category, then review and approve the listing again.

Use `proppi_return_listing_to_draft` for a requested new edit, with the exact current revision and a recovery version only when the service supplies one. Read enquiries through `proppi_list_listing_enquiries({listing_id,page?,rows?})`; read `nextPage` until `hasMore` is false before calling the enquiries complete, and never report an empty page past the last one as a listing with no enquiries (its text says so). No enquiry-reply tool is implied. `proppi_create_campaign({property_id,purpose})`, with `purpose` `sale` or `rental` (not `rent`), creates/reuses a standalone empty campaign when that is the requested work; it does not prepare content or publish a listing.

## Review rental and maintenance work

`proppi_prepare_healthy_homes_review({property_id})` creates a New Zealand review draft. It is not a compliance certificate. For rental renewal notices, `proppi_prepare_rental_renewal_notice_review` requires `property_id`, actual `source_lease_document_ids`, `jurisdiction` (`NZ` for New Zealand, `AU` for Australia) and the current `lease` schema; include the Australian `state` where applicable, pass `recipient_name`/`recipient_email` only as supplied, and preserve unknown lease facts. Both preparation tools start revised work only through their own optional IDs: `changes_requested_deliverable_id` after a change request, `stale_deliverable_id` to regenerate stale work, or `failed_deliverable_id` to retry a failed preparation for the same property. Read/review/accept the result before requesting delivery. `proppi_prepare_tax_summary({property_id, date})` freezes the New Zealand or Australia tax year holding `date` (the property's country decides the year) into a tax summary ready for review, or returns the one already open for that year (`reused` true) with the figures it was frozen with; `matchesLedger` false means those figures differ from the ledger as it reads now, so call `proppi_request_deliverable_changes` on it before presenting them as the year as it stands. It is a working paper for the member's accountant, not tax advice. Changes are made in the property's ledger in Proppi and re-read with `proppi_request_deliverable_changes`; only the member accepts a tax summary, in Proppi.

An accepted rental notice still has not been sent. Use `proppi_request_rental_renewal_notice_send_approval({deliverable_id})`, show the saved recipient and content, then use the specific send approval after explicit consent. Approval only queues the email: it returns `delivery` with the `deliverableId`, `state: "queued"` and `readWith: "proppi_get_deliverable"`. Read `proppi_get_deliverable` for that ID and report `deliverable.rentalRenewalSendOutcome.status` before claiming delivery; never approve again to check. A `failed` status whose `lastError` starts with `Delivery outcome unknown:` means the send was interrupted before the email service confirmed it: the tenant may have received the notice, and Proppi will not resend it. Say exactly that; do not report it as not sent, and suggest the user checks with the tenant before sending the notice another way. If the approval returns an error after confirmation, the notice may still be queued: read the deliverable, do not approve again. When the user confirms in the confirmation panel instead, the panel shows queued, not delivered, and, when the host supports it, passes the same `delivery` receipt to you as model context; read the deliverable the same way. Without that context, read `proppi_get_deliverable` for the notice whose send approval you requested; do not approve again.

Accepted Healthy Homes/Inbox-to-Done work can create internal events, reminders or links. A maintenance reply draft remains a draft. There is no general contractor-dispatch, payment or arbitrary outbound-message tool.

## Approve a saved action

Read `proppi_get_pending_action({action_id})` or discover relevant actions with `proppi_list_pending_actions` (optional `action_type` from the table below, and `limit`). With a `limit`, `hasMore: true` means more are waiting than were returned (`total` counts them all); list again before saying nothing else needs approval. With an `action_type`, only that type is listed, empty or not; list again without it before saying nothing else needs approval. Review the exact target, action type, proposal, expiry and current state. Match the tool to the returned type; never use a general approval for a different operation.

| Saved action type         | Approval tool                               | Arguments                              |
| ------------------------- | ------------------------------------------- | -------------------------------------- |
| `CreateProperty`          | `proppi_approve_property_creation`          | `action_id`                            |
| `CancelMemberTask`        | `proppi_approve_task_cancellation`          | `action_id`                            |
| `ComplianceFollowup`      | `proppi_approve_compliance_followup`        | `action_id`                            |
| `RenameDocument`          | `proppi_approve_document_rename`            | `action_id`                            |
| `SoftDeleteDocument`      | `proppi_approve_document_deletion`          | `action_id`                            |
| `SendRentalRenewalNotice` | `proppi_approve_rental_renewal_notice_send` | `action_id`, `confirmation: "send"`    |
| `PublishPlatformListing`  | `proppi_approve_listing_publication`        | `action_id`, `confirmation: "publish"` |

An approval call for an action that was already executed runs nothing again and returns the recorded outcome with `alreadyApproved: true`; report it as the earlier approval, not a new one. A rejected action, or a pending one past its expiry, is still refused. The first five do not take a `confirmation` field. The send/publish literals are machine arguments used only after actual user consent. For a declined proposal use `proppi_reject_pending_action({action_id})`. To prepare a document rename/bin action, use `proppi_request_document_action_approval` with `document_id`, the discovered `action_type` and `new_title` when renaming. Moving to the bin is not permanent deletion.

## Handle failures and capability limits

- On an authentication/permission error, use the client's existing connection flow and report the specific denied operation. Do not request server credentials.
- On a missing tool or schema mismatch, refresh discovery and inspect the current contract. Never guess replacement names or silently downgrade approval.
- On a stale review/revision, reload and review changed content before another approval. Never invent source versions, review tokens, choice IDs or receipts.
- On a timeout, inspect the saved task/action/deliverable or publication outcome. If external effects are uncertain, report uncertainty and avoid another send/publication attempt until reconciled.
- Accounting support here means evidence retrieval, preserved amounts/currencies, fact review and briefs. It does not post ledger entries or move money. Local service coordination still needs a supported channel and explicit user instruction.
